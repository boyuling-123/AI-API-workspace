# 开发决策记录

## ADR-001：保留远端历史并迁移本地工作树

- 决策：重新克隆远端仓库，在新目录中迁移当前本地源码。
- 原因：当前开发目录没有 `.git`，直接初始化会丢失远端历史和 PR 基线。
- 约束：原目录不覆盖、不删除；迁移排除密钥与生成产物。
- 回滚：删除新工作目录即可；远端 `main` 和原开发目录均不受影响。

## ADR-002：能力状态采用六态模型

- 状态：未规划、设计中、Demo、部分实现、已实现、已验证。
- “已验证”必须同时具备代码证据、真实测试证据、验收条件、CI 和截图或 Trace。
- 页面、PRD 与能力矩阵必须使用相同口径。

## ADR-003：主题可拆成多个连续小 PR

- 十个主题只用于路线分组，不强制一个主题对应一个长期分支。
- 每个 PR 只处理 1 至 3 个相互关联且可独立验收的能力。
- 每次合并后从最新 `main` 创建下一分支。

## ADR-004：运行策略随任务固化，自动重试只处理瞬时错误

- QPS、单次超时和重试上限作为 Task 快照持久化，暂停续跑不得读取页面上的新值覆盖原策略。
- QPS 限制真实 HTTP 启动次数而不是业务 Case 数，首次调用与重试必须共享同一全局限速器。
- 只有超时、限流、网络和服务端错误允许自动重试；鉴权、请求配置、解析和未知错误直接失败，禁止无意义消耗。
- 重试次数有限且产品上限为 3；暂停和终止必须同时打断限速等待、退避等待和活动请求。

## ADR-005：定向重跑创建新任务并保存稀疏调用计划

- 原任务和原结果是不可变的历史证据；失败项或指定 Case 重跑必须创建新 Task，不在原 Task 上覆盖结果。
- 重跑范围保存为明确的 `inputId + targetId` 组合，执行、检查点和暂停恢复都使用同一稀疏计划，禁止退化成完整笛卡尔积。
- 失败项仅包含原结果中的 `error` 组合；指定 Case 使用原任务当前仍存在且可运行的目标。已删除或未测试通过的目标在预览中提示并排除。
- 真正调用前必须展示调用数并由用户确认；重跑可能产生模型费用，但不得联动启动 AI 评价。
- 新评价维度涉及独立评价数据流，继续拆分为后续短生命周期 PR。

## ADR-006：新增目标只产生增量调用，历史结果显式复用

- 新增模型或算法重跑只把用户确认的 `Case + 新目标` 写入稀疏调用计划，源任务已有目标不得再次请求。
- 新任务复制所选 Case 的终态历史结果用于同屏对比，并在每个结果上保存 `reusedFromTaskId`；页面与 Excel 必须显示“历史复用”，禁止伪装成本次调用。
- 检查点进度和任务最终状态只统计本次稀疏计划，历史复用结果不增加调用总数，历史失败也不改变新增调用的完成状态。
- 历史目标即使已从当前配置删除，仍可作为只读结果展示；只有本次真正执行的新目标必须存在且已测试可用。
- 用户必须显式选择新增目标和 Case，并在调用预览确认后才能启动；不得自动启动 AI 评价。

## ADR-007：新增评价维度复用历史输出并独立留档

- 新增维度从评价历史显式发起，复用来源 Task 的终态模型输出，禁止重新请求任何被测模型或算法。
- 评价范围锁定为来源评价实际完成的输入，确保新旧维度样本口径一致；标准答案模式仍按已确认字段跳过缺失答案的行。
- 来源根评价及其增量记录组成一条评价血缘。新维度名称按大小写和连续空白归一化，禁止与血缘中任何已有维度重复。
- 真正调用前必须展示 Judge 调用数、被测模型调用数、复用输出数和新增维度数；用户确认前不得发送 Judge 请求。
- 每次新增维度生成独立 EvaluationRecord，只保存本次新维度结果与根 `sourceEvaluationId`，不得覆盖或合并修改历史评价。

## ADR-008：维度生成使用结构化上下文与有界代表性样本

- 维度生成请求必须显式包含评测目标、业务场景、任务类型和至少一条代表性输入输出样本；服务端在调用模型前执行同一份 Schema 校验。
- 代表性样本从当前 Task 的真实输入与跑批结果确定性抽取，默认覆盖首、中、尾，也可优先失败项或标准答案；最多 8 条，用户在发送前可预览并排除。
- 数据最小化是服务边界约束：只传截断文字、可用标准答案、输出状态、图片数量和错误类型，禁止发送原始图片、base64、完整错误文本或任意额外字段。
- 样本文字一律视为待分析数据而非系统指令；Prompt 必须明确禁止服从样本中的要求，降低数据内提示注入的影响。
- OpenJudge 未接入前必须在页面和文档明确标识，当前实现继续使用已配置的通用模型与内部预设，不得冒充 OpenJudge 或完整 Rubrics Generator。
- 维度生成和正式 AI 评价保持两个显式动作：生成只在用户点击后发生，候选维度仍需人工确认，任何情况下都不得自动启动 Judge 评价。

## ADR-009：硬规则与 Bad Case 只能通过显式、有界契约进入维度生成

- 硬规则在页面中按换行拆分，每行一条；按大小写和连续空白去重，最多 20 条、单条最多 500 字。禁止把任意 JSON、段落或自然语言自动猜成规则。
- Bad Case 只能由用户显式标记，或来自 `bad_case`、`is_bad_case`、`badCaseReason` 等有限白名单列名；普通 prompt 和未知字段中的“坏例”文字不得触发标记。
- 每条 Bad Case 必须填写最多 1000 字的原因。原因缺失、规则超限、重复规则或非法外部 API 请求都必须在模型调用前失败。
- 发送维度生成请求前在客户端脱敏，服务端解析外部请求时再次脱敏；请求仍只保留截断文字、标准答案、状态、图片数量和错误类型，不包含原图、base64 或完整失败日志。
- 硬规则与 Bad Case 只影响候选维度生成。生成按钮仍是显式动作，生成后仍需人工确认，且不得联动调用 `/api/evaluate`。
- 人工评分、排序与 Iterative Rubrics Generator 属于独立反馈数据流，留给后续短生命周期 PR，不在本轮用 Bad Case 原因冒充人工评分。

## ADR-010：人工反馈按 Case 与目标显式绑定，当前只作为受控上下文

- 人工反馈只允许附着到已选代表性 Case，并精确绑定该 Case 当前全部目标输出；缺失、重复或未知目标 ID 必须在模型调用前失败。
- 人工评分与偏好排序是互斥模式。评分范围为 `0–10` 且最多 1 位小数；排序至少需要 2 个目标，并完整、唯一覆盖 `1..N`，其中 1 为最佳。
- 用户切换反馈模式时清空旧数值，避免把分数误作名次；可选备注最多 1000 字，并在客户端组包和服务端解析两层脱敏。
- 当前通用维度生成模型只能把人工信号用于解释质量差异，不得把分数或名次本身当作评价维度，也不得自动触发正式 AI 评价。
- OpenJudge 与 Iterative Rubrics Generator 仍未接入。真正的迭代生成必须有多轮候选、反馈更新与前后差异证据，不能用一次 Prompt 拼接冒充。

## ADR-011：新评价使用完整结构化 Rubric，旧历史保持只读兼容

- 新建评价维度必须完整包含名称、定义、`0/5/10` 三档评分锚点、`1–5` 条证据要求和可执行判断规则；缺任一字段都不能生成 Judge Prompt 或启动评价。
- 无人工评分或偏好排序时，当前通用模型执行一次 Simple Rubrics 生成；存在人工反馈时仍是一次受控上下文生成。OpenJudge 与 Iterative Rubrics Generator 的状态不因此改变。
- AI 返回的旧式 `name/desc` 或不完整 Rubric 必须报错，不允许服务端静默补字段；只有用户在页面显式点击模板按钮时，才可按已填写定义生成可继续审阅的通用锚点。
- Prompt 生成接口和最终 Judge 接口必须在模型调用前重复执行同一 Schema 校验，并把完整 Rubric 原样写入模型 Prompt，确保前端门禁不能被绕过。
- `EvalDimension` 的新增字段保持可选，仅用于读取既有历史数据；旧记录仍可展示和参与评价血缘去重，但任何新的模型调用都必须使用完整结构。
- 本轮不实现权重、一票否决、Evaluator 版本化、OpenJudge 或多轮迭代校准，这些能力继续按各自状态和短生命周期 PR 推进。

## ADR-012：Judge 独立打分，平台确定性执行权重与一票否决

- 权重使用百分比表示，单项范围为 `0.01–100` 且最多两位小数；已选维度必须精确合计 `100%`。服务端不得为缺失或非法权重静默补默认值。
- 页面在维度选择集合变化时按基点稳定平均分配，用户可以继续手动调整；任何 Rubric、权重或否决阈值变化都会改变策略指纹，使旧确认立即失效。
- 一票否决是维度级可选规则，阈值范围为 `0–10` 且最多一位小数；实际得分严格低于阈值时触发，等于阈值不触发。
- Judge 只负责输出独立维度分数和理由，不负责权重算术或最终否决。平台在解析并补齐维度分后，根据已确认策略确定性计算加权分、否决状态和原因。
- Prompt 生成和正式 Judge 路由必须在任何模型调用前复验完整策略；即时结果、历史和 Excel 使用同一组平台计算字段。
- 新增策略字段保持可选以兼容旧历史，但所有新 Prompt 与 Judge 调用必须使用完整策略。本轮不创建版本化 Evaluator，也不冒充 Judge 校准或发布门禁。

## ADR-013：Evaluator 与 Prompt 采用只追加的不可变版本

- 一个 Evaluator 家族使用稳定 `evaluatorId`，每次保存按已有最大版本号追加 `vN+1`；不得原地更新或覆盖历史版本。
- 版本快照包含裁判模型、评测目标、完整 Rubric、权重、一票否决、Prompt、评价模式和标准答案字段，同时记录修改人、时间、变更说明与适用任务。
- 执行定义指纹用于判断页面草稿是否仍绑定已保存版本；身份与元数据再由完整性指纹保护，任一快照字段被篡改时禁止加载。
- 手动修改 Prompt 或策略只形成未保存草稿；用户可继续无版本评价以兼容旧流程，但历史会明确显示“未绑定版本”。保存或加载版本本身绝不启动 Judge。
- 新字段在 `Project` 与 `EvaluationRecord` 中保持可选，不提升 Schema 版本，避免删除已有本地项目；新建项目显式初始化空版本列表。
- 所有版本文本在进入项目存储前经过统一脱敏，脱敏函数必须对既有 `[REDACTED]` 占位符保持幂等。

## ADR-014：版本 Diff 本地确定性计算，恢复只能追加新版本

- 版本 Diff 只允许比较同一 Evaluator 家族且完整性校验通过的快照；损坏版本与跨家族版本必须直接拒绝，不能降级为不可信的近似比较。
- 结构化 Diff 覆盖裁判模型、评测目标、评价模式、标准答案字段、适用任务和完整 Rubric/策略；Prompt 另做逐行文本 Diff，并将变化映射为明确影响范围。
- Prompt 逐行 Diff 设固定计算上限；超大文本使用共同前缀与后缀的有界替换算法，避免二次复杂度导致浏览器卡死。
- 恢复只针对非最新版历史快照，通过既有不可变版本创建函数追加 `vN+1`；来源、已有中间版本和历史评价记录不得修改或删除。
- 恢复版本记录操作者、当前适用任务和“从 vN 恢复”的变更说明。Diff、预览、选择和恢复本身都不得调用 Judge 或启动评价。
- Prompt 试跑与 Judge 校准仍属于后续独立能力，本轮不以 Diff 或恢复冒充发布校准。

## ADR-015：Evaluator Active 必须通过可复算的固定校准门禁

- Active 发布只接受同一 Evaluator 家族、相同完整执行定义且判定标准逐字同步的校准运行；同定义的元数据版本可复用证据，但跨家族和自定义标准不得旁路。
- 正式阈值固定为至少 20 个成功 Case、准确率不低于 90%、Cohen's κ 不低于 0.8、Bad Case 漏判率不高于 5% 且零错误；调用方不能覆盖阈值。
- 发布前必须检查 Case ID 唯一和结果结构，并从逐 Case 结果重新计算指标；已存指标与复算结果不一致时直接阻断，不能信任展示值。
- 门禁通过不等于自动发布。用户仍需填写发布人并二次确认；发布动作不调用 Judge、不调用被测模型，也不联动启动正式评价。
- 每次发布追加不可变记录并引用上一条 Active；旧记录不覆盖，完整性损坏的记录不参与当前 Active 选择。
- 当前为本地单用户管理平台，本轮不冒充服务端权限控制。查看、运行、配置和发布角色继续由 SEC-005 专题实现。

## ADR-016：多 Judge 使用独立调用矩阵和确定性保守仲裁

- 多 Judge 校准选择 `2-5` 个唯一 Judge；精确调用数固定为黄金 Case 数乘以 Judge 数，全部调用共用一个受控并发池。
- 每个 Judge 只看到单个 Case 与同一份已确认标准，不发送人工真值、复核说明或其他 Judge 的结果，避免投票相互污染。
- 原始投票和逐 Judge 指标必须完整保存。任一 Judge 缺失或失败时，该 Case 记为错误，不使用部分票数静默生成结论。
- `majority_conservative` 使用多数票且平票固定为 `fail`；`unanimous_pass` 只有全票通过才判为 `pass`。策略与 Judge 集合共同形成稳定运行身份。
- 发布门禁必须从原始投票复算仲裁、逐 Judge 指标、最终指标与分歧数，并把 Judge 集合和仲裁策略冻结到发布快照；篡改任一证据都阻断 Active。
- 单 Case API 保持不变，客户端负责显式矩阵编排。PR 06G 只交付核心与测试，PR 06H 再接入显式多选、精确费用确认、逐 Judge 指标和原始票下钻；两层均验收后 JUDGE-005 已升级为“已验证”。

## ADR-017：平台总览只组织真实能力，不替代业务工作台

- “跑批”继续作为默认首页和导航第一入口，批量运行控制台仍位于输入与目标选择之前；平台总览通过独立标签和 `?tab=overview` 深链访问。
- 总览只读取当前 `Project` 的目标、任务、评价、黄金集、校准和发布记录，不发起 API 请求、不启动模型调用，也不创建另一套状态数据源。
- 六条产品链路使用能力矩阵的正式状态词。Agent 外部召唤标为 Demo，多 Judge 页面闭环标为已验证，20GB 级数据后端化标为设计中，禁止用营销文案伪装成生产能力。
- 总览卡片只导航到既有真实页面；AI 评价仍必须先从跑批历史选择批次，不能从总览直接绕过数据源和费用确认门禁。
- 390px 移动端必须无页面级横向溢出；顶部工具栏在窄屏采用弹性项目名和固定触控按钮，桌面端保留现有标签与布局。

## ADR-018：校准风险由固定规则生成，人工复核使用只追加覆盖层

- 风险入队不调用模型。规则固定覆盖 Judge 错误、Bad Case 漏判、人工与 Judge 分歧、多 Judge 内部分歧、低于 `75%` 的置信度，以及同一黄金集家族 Case 的跨运行重复风险。
- 每条风险必须显示代码、中文名称、具体依据和分数；队列按严重度、总分、重复次数、运行时间稳定排序，禁止使用不可解释的隐藏权重或随机排序。
- 人工复核必须先领取再完成。完成时必须选择确认、改判 pass/fail 或待后续处理并填写说明；只有领取人可以提交，重复领取与重复完成均被拒绝。
- 领取与完成都追加不可变事件，保存原始人工标签、原始 Judge 标签、风险快照、操作者、时间和完整性指纹；人工结论是展示与报告的覆盖层，不得改写 Judge 投票、仲裁结果或黄金标签。
- 完整性失败的事件必须告警并从队列状态推导中排除，不能静默信任；敏感文本进入本地项目存储前继续统一脱敏。
- 当前仍是本地单用户管理平台，领取用于流程协作和留痕，不冒充服务端事务锁或权限系统；多用户并发与角色权限留给后端及 SEC-005 专题。

## ADR-019：评价排行榜由历史原始分数确定性派生，缺失值不补零

- 排行榜只读取 `EvaluationRecord` 已保存的维度分数，不调用 Judge、不调用被测模型，也不写回原评价记录；切换维度只是页面派生视图。
- 综合榜先在每个 Case 内按所选维度原权重重新归一，再跨 Case 求平均；旧记录缺少完整权重时对所选维度等权，不伪造原始权重。
- 任一所选维度缺失、非有限或超出 `0–10` 时，该目标在该 Case 的覆盖记为缺失，不允许补零、截断或只用剩余维度悄悄计算。
- 只有覆盖全部评价 Case 的目标获得正式名次；覆盖不足的目标仍展示已有分数、覆盖率和原始否决次数，但明确标记不参与名次。
- 正式榜按分数降序，同分采用竞赛排名并以稳定目标 ID 保持展示顺序；计算边界统一消除浮点尾差，确保刷新和不同运行环境结果一致。
- 排行榜必须提供原始 Case 明细入口，保留输入、输出、模型、各维度分数、理由和策略结果；本轮不冒充跨项目 Benchmark、统计显著性或人工覆盖系统。

## ADR-020：评价风险筛选以完整 Case 为单位并保留可解释依据

- 低分默认定义为任一目标的有效加权分严格低于 `6`；模型分歧默认定义为同一 Case 至少两个有效目标的最高与最低加权分差不低于 `2`。两个阈值允许在 `0–10` 内显式调整。
- 高风险固定定义为任一目标命中已保存的一票否决，或有效加权分不高于 `3`；失败固定覆盖来源运行失败、中断、未完成、缺少结果，以及来源成功但评价分缺失或非法。
- 评分优先使用历史保存的 `weightedScore`。旧记录缺少该字段时，只有全部历史维度分合法完整才按原权重补算；缺失、非有限或越界分数不得补零、截断或写回原记录。
- 多类筛选明确支持“匹配任一条件”和“同时匹配全部”两种语义；清除筛选同时恢复默认阈值与完整 Case 集，筛选状态不进入项目持久化。
- 筛选和导出均以完整 Case 为最小单位，不允许只导出命中模型而丢失同 Case 的对照结果。Excel 除原始输入、输出和评分外，还附带命中类型、最低加权分、模型分差和具体依据。
- 全流程只读取本地历史，不调用 Judge 或被测模型，也不自动启动评价；人工改分、Bad Case 标记、Judge 引用证据与 HTML 报告继续由独立短 PR 实现。
